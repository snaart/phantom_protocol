# Pre-1.0 Deferred Follow-ups

> **For agentic workers:** Each section below is a self-contained follow-up
> with scope, prerequisites, effort estimate, and exit criteria. None
> blocks 1.0; all are tracked so future contributors find the breadcrumbs
> instead of rediscovering scope from scratch.

This plan captures three substantive items called out during the
post-Phase-8 polish sweep (commits `43aad3b`..`171c222`, May 2026). They
were deliberately **not** implemented in that sweep because each is a
multi-day undertaking with design decisions that benefit from a dedicated
PR and reviewer attention. Status is **planned, design-locked** — the
shape of each task is known.

## 1. Full FIPS 140-3 primitive swap behind the `fips` feature

**Status:** ⏳ planned. Scaffold landed in commit `d4d121b` (`fips`
Cargo feature exists, enabling it fails the build with a clear
`compile_error!()` pointing here).

### Scope

Swap every cryptographic primitive that is **not** on the FIPS 140-3
Approved-Algorithms list with a FIPS-validated equivalent, gated by the
`fips` Cargo feature. The result: with `--features fips` the binary is
buildable, all CAVP tests still pass, and `crypto::self_tests::run_post`
is wired into the bootstrap.

| Current | Replacement under `fips` | Notes |
| --- | --- | --- |
| `ring::aead::AES_256_GCM` | `aws-lc-rs::aead::AES_256_GCM` | FIPS-validated module (AWS-LC). Same API shape. |
| `chacha20poly1305` | dropped | Not FIPS-approved. Reject `CipherSuite::ChaCha20Poly1305` at handshake. |
| `x25519-dalek` (KEM half) | ECDH-P-256 via `aws-lc-rs::ecdh` | Or PQ-only mode (skip the classical half entirely — design call). |
| `blake3` (used as KDF / cookie hash) | HKDF-SHA256 / SHA-256 | Every `blake3::derive_key(label, &input)` becomes `Hkdf::<Sha256>::new(None, &input).expand(label, ...)`. The PoW gate's `blake3::hash` stays — PoW is not a FIPS-relevant primitive. |
| `getrandom` (default RNG) | `aws-lc-rs::rand::SystemRandom` (CTR_DRBG, SP 800-90A) | Plumb through `RngProvider` so the `OsRng` impl switches under the feature. |

Additionally:

- `crypto::self_tests::run_post()` (commit `2dbe1cd`) must be called
  from `PhantomListener::bind*` / `PhantomSession::connect*` **once**
  per process under `fips`. Use a `std::sync::OnceLock<bool>` or
  `Once::call_once` to guarantee single-shot.
- Remove the `compile_error!()` in `core/src/lib.rs` once the swap is
  complete.

### Prerequisites (all done)

- `crypto::self_tests::run_post` exists (commit `2dbe1cd`).
- `fips` feature flag exists in `core/Cargo.toml` (commit `d4d121b`).
- CAVP vectors exist in `core/tests/cavp.rs` (Phase 5.4 ✅).
- `docs/compliance/fips-readiness.md` documents the gap analysis.
- `RngProvider` trait exists (Phase 3.8 ✅) — the seam for the DRBG swap.

### Out of scope

- CMVP / CC lab validation (Phase 5.7 ⏭️ — external procurement).
- Formal verification (Phase 6.10 ⏭️).

### Estimated effort

3–5 working days. The mechanical primitive swap is straightforward
once the `aws-lc-rs` integration is wired; the design call is
"ECDH-P-256 hybrid or PQ-only" — a one-meeting decision.

### Exit criteria

- `cargo check --features fips` passes (no more `compile_error!()`).
- `cargo test --features fips` runs the full suite green.
- A new CI matrix entry in `.github/workflows/ci.yml` runs the suite
  under `--features fips`.
- `docs/compliance/fips-readiness.md` flips every "gap" row to
  "implemented".

## 2. WASI leg + runtime for `wasm32-wasi`

**Status:** ⏳ planned. `wasm32-wasi` remains `allow_failure: true` in
`.github/workflows/cross.yml` — the only `allow_failure` entry in the
12-triple matrix. Scope is documented in `docs/operations/wasi.md`.

### Scope

Add two pieces so the `wasm32-wasi` cross-compile becomes a hard CI
gate alongside `wasm32-unknown-unknown` and `thumbv7em-none-eabihf`:

1. **`transport::legs::wasi`** — a `SessionTransport` impl on top of
   the WASI socket API (`wasi::sockets`). Same 4-byte BE length-prefix
   framing as `TcpSessionTransport`. The wasm32-unknown-unknown side
   has `WebSocketLeg`; the WASI side gets a TCP-shaped equivalent so
   the same Phantom session machinery runs inside a WASI runtime
   (wasmtime, wasmer, jco).
2. **`runtime::wasi_runtime::WasiRuntime`** — `Runtime` impl using
   `wasi::clocks::monotonic_clock` + `wasi::clocks::wall_clock` and a
   poll-loop executor (similar to `EmbeddedRuntime` but using
   `wasi::poll::poll_oneoff`). No threads — WASI 0.2 is single-task
   per instance.

### Prerequisites

- WASI Preview 2 stabilization in upstream `wasi` crate (target version
  documented in `docs/operations/wasi.md`).
- Settling of the `wit-bindgen` / `wasi-cli` API surface — moving target
  as of 2026-05.

### Out of scope

- WASI Preview 1 support (Preview 1's socket API is too constrained for
  Phantom's leg model).
- Running phantom-server as a WASI guest. The leg is for client-side
  embeddings (e.g. wasmtime-hosted apps proxying through Phantom).

### Estimated effort

4–6 working days, *gated on upstream WASI Preview 2 reaching a stable
release*. The implementation itself is a few hundred lines; most of
the effort is wrestling with WASI ecosystem moving parts and adding
host-side integration tests (likely via wasmtime).

### Exit criteria

- `cargo check --target wasm32-wasi` clean under default features.
- `wasm32-wasi` row in `.github/workflows/cross.yml` flips from
  `allow_failure: true` to a hard gate.
- A host-side integration test in `core/tests/` that boots a wasmtime
  guest carrying a Phantom session and round-trips a payload through
  a real `WasiLeg`.

## 3. `core/src/networks/` layer maturation

**Status:** ⏳ planned. CLAUDE.md describes the layer as "currently
skeletal" — `pipeline.rs` / `engine.rs` (trait-based packet processing)
and `transport.rs` / `tls.rs` (Rustls config for HTTPS legs) exist but
provide minimum viable scaffolding; the actual routing / retry / error
propagation surface is undeveloped.

### Scope

Build out the `networks` layer into a real higher-level routing
surface that sits between `api::PhantomSession` and the multi-path
scheduler. Concretely:

1. **Routing policy** — beyond the current round-robin / low-latency
   selection in `transport::scheduler`, add per-stream routing
   constraints: pin-to-path, fallback-class, latency-sensitive vs
   bulk. Today every stream rides the scheduler's global preference.
2. **Retry + error propagation** — when a leg fails (e.g. KCP UDP
   socket errors), the layer should retry on another leg before
   surfacing `CoreError::NetworkError` to the API caller. Current
   behavior is fail-fast.
3. **HTTPS leg wiring** — `networks/tls.rs` configures a Rustls
   `ClientConfig` but nothing consumes it. Either delete the file or
   wire it into a new `transport::legs::https` (cookie-PoW gate over
   HTTPS, useful for hostile network egress).
4. **Engine ↔ scheduler bridge** — `NetworkEngine` in `engine.rs`
   exists as a stub; either grow it into the routing-policy enforcer
   above or remove it and inline the trivial bits into
   `transport::scheduler`.

### Prerequisites

- Multi-path validation (Phase 4.2 ✅) — already done; the policy
  layer needs validated paths to route over.
- A concrete consumer use case. Current users hit
  `transport::scheduler` directly with sensible defaults; the
  motivation for `networks/` is "we want to expose policy knobs," not
  "the current routing is broken."

### Out of scope

- A configuration language / DSL for routing rules. JSON / TOML
  routing manifests are out of scope; expose a typed Rust builder
  API instead.

### Estimated effort

5–8 working days, but **only with a concrete consumer use case
driving it**. Building the layer speculatively risks shipping API
that nobody uses. The current skeletal state is fine until a real
embedder asks for routing policy.

### Exit criteria

- A documented `RoutingPolicy` type exposed via `phantom_core::networks`.
- At least one production embedder (`phantom-server` or a sibling)
  consumes the policy API.
- `transport::scheduler` becomes an implementation detail of
  `networks::engine` rather than a peer API surface.
- CLAUDE.md `### 6. Networks layer` section is no longer prefixed
  "currently skeletal".
